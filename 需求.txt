任务：给 DSH 桌面版写一个本地客户端插件 dsh-recent-usage-metrics，在「设置 → 通用 → 性能与用量」
里增加第三个选项「极客」。选中后，输入区底部状态栏最左侧实时显示最新一次请求的极客级指标，
并可点击展开一个磨砂玻璃抽屉，列出最近 10 次请求的完整指标。

本文件是【已实现版本的完整规格】。照此文档实现，应得到一致的效果与行为。
文档中给出的关键代码为最终生效代码，可直接使用。

三、五个指标的准确定义（最重要，务必逐条实现）
================================================================================

一个「请求」= 一个已结算的 assistant step。Chat 快照里 legacy.nodes 中 kind==='assistant'
的节点，每个带有：

    node.timing.stepStartTime    步骤开始（= step/start 事件时间）
    node.timing.firstTokenTime   第一个 token 的时刻（可能为 null，见第八节）
    node.timing.completedTime    流结束时刻
    node.usage.outputTokens      上游返回的精确输出 token 数
    node.blocks                  内容块数组

定义：

  1) 首字时间 TTFT = firstTokenTime − stepStartTime
  2) 总用时        = completedTime − stepStartTime
  3) 输出 Token    = usage.outputTokens（精确值，见第四节）
  4) 实时速度      = 输出 Token ÷ (completedTime − firstTokenTime)，即真正解码阶段的速率
  5) 折算速度      = 输出 Token ÷ 总用时

  单位：时长 " s"，速度 " tok/s"，Token " tok"（数字与单位之间一个空格）。

  【不要】把 reasoningTokens 加到 outputTokens 上：DSH 的 outputTokens 已包含推理 token。

================================================================================
四、Token 的来源与估算（精确 vs 估算）
================================================================================

优先级 1：上游 usage.outputTokens —— 这是权威值，必须优先使用。
  从 node.usage 读取，兼容两种拼写：outputTokens / completionTokens / completion_tokens。
  实测：一个真实会话日志的 262/262 个已结算步骤都带 outputTokens，即正常情况下永远是精确值。

优先级 2：字符估算 —— 仅当上游确实没返回 usage 时（中断/失败的请求）。
  此时该行标记为估算，界面在所有相关数字前显示 ~。

【字符估算的系数是实测标定的，不要随手改成 /4 一刀切】
内容不同质：
  - 正文与推理（text / reasoning）：约 4 个 ASCII 字符 / token
  - 工具调用参数（tool-call 的 argsRaw）：是 JSON，短键名 + 标点 + 引号，
    分词效率明显更差，约 2.5 个 ASCII 字符 / token
  - CJK 字符：1 字符 / token

  实现：

    const CJK_CHAR =
      /[\u2e80-\u303f\u3040-\u30ff\u3400-\u4dbf\u4e00-\u9fff\uac00-\ud7af\uf900-\ufaff\uff00-\uffef]/g
    const CHARS_PER_TOKEN_PROSE = 4
    const CHARS_PER_TOKEN_TOOL_ARGS = 2.5

    function tokensOfSegment(text, charsPerToken) {
      if (typeof text !== 'string' || text === '') return 0
      const cjk = text.match(CJK_CHAR)?.length ?? 0
      const rest = Math.max(0, text.length - cjk)
      return cjk + rest / charsPerToken
    }

    // 累加各段，最后只取整一次（避免多块各自取整累积损失）
    function estimateTokens(blocks) {
      let total = 0
      for (const block of blocks ?? []) {
        if (block === null || typeof block !== 'object') continue
        if (typeof block.text === 'string') total += tokensOfSegment(block.text, CHARS_PER_TOKEN_PROSE)
        else if (typeof block.argsRaw === 'string') total += tokensOfSegment(block.argsRaw, CHARS_PER_TOKEN_TOOL_ARGS)
      }
      return Math.round(total)
    }

  标定依据（725 个已结算步骤，与上游 outputTokens 对比，取中位绝对对数误差）：
    全部用 /4 一刀切          → 0.363（典型低估 30%，这就是"折算速度看起来偏小"的成因）
    正文 /4 + 工具参数 /2.5   → 0.127（估计/实际 的中位数 = 1.00）
  细网格搜索的理论最优是 0.125，上述规则与之相差 0.002，且更简单。
  CJK 系数保留惯例的 1：样本中仅 45% 的步骤含中文，该参数在样本里不可辨识，
  拟合出来是噪声。

================================================================================
五、实时（生成中）指标怎么算 —— 两个已修复的坑，必须按此实现
================================================================================

生成中的请求在 Chat 快照里只有 legacy.partial = { turn, step, blocks }。
它【没有】任何时间字段，所以实时指标需要自己推导。

坑 1：首字时间的起点必须用「步骤起点」，不能用「轮次起点」
------------------------------------------------------------------
真实日志实测：同一轮里，从轮次开始到第 2 步及以后各步开始的间隔，
中位数 174 秒，最大 2720 秒，549/558 个非首步超过 1 秒。
若用 turnTimings 里的轮次起点，实时首字会显示几十秒；
等这轮结束变成精确值时又变回几秒 —— 这正是"思考中显示几十秒、完成后只有几秒"的成因。

正确做法：用「同轮中最近一个已结算步骤的 completedTime」作为步骤起点
（下一步紧接着它开始），只有整轮第一步才回退到轮次起点（实测仅差 26 ms）。

    function stepStartOf(partial, nodes, turnTimings) {
      const turn = partial?.turn
      const step = partial?.step
      let previous = null
      for (const node of nodes ?? []) {
        if (!isAssistantNode(node)) continue
        if (node.turn !== turn) continue
        if (!(node.step < step)) continue
        const completed = numberOrNull(node.timing?.completedTime)
        if (completed !== null && (previous === null || completed > previous)) previous = completed
      }
      if (previous !== null) return previous
      return numberOrNull(turnTimings?.get?.(turn)?.startTime)
    }

坑 2：首字时刻以「新 partial key 出现的那一刻」为准
--------------------------------------------------
精确值的 firstTokenTime 由 Chat 从 token 增量累积，reasoning 和 tool-call 增量都算。
而 legacy.partial 只在步骤有可见内容后才出现，所以「新的 key 出现的瞬间」就是首字时刻。
不要等 blocks 里出现非空 text 才记时 —— 那会让长推理的步骤首字明显偏大。

    useEffect(() => {
      if (!running) { observation.current = { key: null, firstTokenAt: null }; return }
      const key = `${partial.turn}:${partial.step}`
      if (observation.current.key !== key) {
        observation.current = { key, firstTokenAt: Date.now() }
        return
      }
      if (observation.current.firstTokenAt === null && blocksHaveText(partial.blocks)) {
        observation.current = { key, firstTokenAt: Date.now() }
      }
    }, [running, partial])

坑 3：工具调用参数在流式期间不在 blocks 里，必须另外读
--------------------------------------------------------
真实日志实测：853/874 个步骤（98%）带工具调用参数，
且这些参数占该步骤估算 token 的【中位数 93%】。

但 Chat 存储层处理 tool-call-delta 时是「原样复制、不追加」：

    case "tool-call-delta": {
      argsRaw: previous?.kind === "tool-call" ? previous.argsRaw : ""
      //                                            ↑ 只保留，不累加
    }

所以 argsRaw 在整个流式过程中是空串，直到 block-end 才一次性填入。
只读 blocks 的话，写文件期间 token 数会完全不动，直到结束时突然跳一大截。

参数增量其实存在：Chat 把它累积在调用自身的 args.chunks 上
（PartialArguments 的公开字段），通过 legacy.runningCalls 暴露给客户端。
对 phase === 'preparing' 的调用读取它，并按工具系数折算计入实时 token：

    function preparingArgsText(runningCalls) {
      let text = ''
      for (const call of runningCalls ?? []) {
        if (call === null || typeof call !== 'object') continue
        if (call.phase !== 'preparing') continue
        const chunks = call.args?.chunks
        if (Array.isArray(chunks)) {
          for (const piece of chunks) if (typeof piece === 'string') text += piece
          continue
        }
        if (typeof call.argsRaw === 'string') text += call.argsRaw
      }
      return text
    }

    const tokens = estimateTokens(partial.blocks)
      + Math.round(tokensOfSegment(preparingArgsText(runningCalls), CHARS_PER_TOKEN_TOOL_ARGS))

其他实时细节：
- 每 150 ms 刷新一次 now（setInterval），步骤结束后必须 clearInterval。
- 实时值一律标记为估算（显示 ~），步骤结算后立刻被精确值替换。
- 生成中时 legacy.partial.blocks 里 reasoning 也是 kind:'reasoning' 且带 text 字段，
  所以估算天然覆盖推理内容，不需要特殊处理。

================================================================================
六、气泡的固定宽度布局（防抖动的核心，必须照做）
================================================================================

目标：任何一个数字变化（9.8→10.2、445→96、-- 占位、~ 出现或消失），
整体宽度【一像素都不变】。

做法：把固定宽度设在【数字元素】上，绝不设在包裹数字+单位的格子上。

  .dsh-rum-parts { display: inline-flex; align-items: baseline; gap: 10px; }
  .dsh-rum-part  { display: inline-flex; align-items: baseline;
                   font-variant-numeric: tabular-nums; white-space: nowrap; }
  .dsh-rum-num   { flex: none; display: inline-block; text-align: right;
                   font-variant-numeric: tabular-nums; }
  .dsh-rum-unit  { flex: none; white-space: pre; }   /* pre 保留前置空格 */
  .dsh-rum-tilde { flex: none; display: inline-block; width: 1ch; text-align: center;
                   visibility: hidden; }              /* 恒定占位，只切换可见性 */
  .dsh-rum-tilde[data-on="true"] { visibility: visible; }

  .dsh-rum-part[data-metric="ttft"] .dsh-rum-num,
  .dsh-rum-part[data-metric="total"] .dsh-rum-num    { width: 4.5ch; }
  .dsh-rum-part[data-metric="speed"] .dsh-rum-num,
  .dsh-rum-part[data-metric="amortized"] .dsh-rum-num { width: 4.5ch; }
  .dsh-rum-part[data-metric="tokens"] .dsh-rum-num    { width: 5.5ch; }

【血泪教训，务必避免】
- 不要把 width 设在 .dsh-rum-part 上。格子里还有单位文本，4ch 装不下「2.3 s」，
  单位会被裁掉，现象是"数字和单位显示不全"。
- 状态栏格子和抽屉格子【必须用不同类名】（本实现用 dsh-rum-part vs dsh-rum-col）。
  曾因共用 dsh-rum-cell 类名，抽屉那条 overflow:hidden + text-overflow:ellipsis
  把状态栏的单位也裁掉了。
- 不要用 min-width。设了下限但数字继续变长时仍会推开宽度，抖动照旧。
- 数字之间不要放 · 之类分隔符，改用 parts 上的固定 gap。
- 估算标记 ~ 必须是常驻的 1ch 元素，只切 visibility，不能插入/删除节点。

    backdrop-filter: var(--dsw-menu-backdrop-filter);      /* blur(40px) saturate(150%) */
    --dsw-elevation-stroke-color: var(--dsw-alias-border-l1);
    box-shadow: var(--dsw-elevation-prominent);
    border-radius: var(--dsw-radius-lg);
    padding: 16px;
    color: var(--dsw-alias-label-secondary);
    font-size: 12px; line-height: 18px;

【禁止】用 color-mix(... var(--dsw-alias-bg-overlay) ...) —— 那会比原生明显更透。

【定位】position: fixed 挂到 document.body（用 createPortal），避免被父容器裁剪。
  右边缘与气泡右边缘对齐：用 right 偏移，不用 left + translateX(-50%)。
  动画只做 translateY + scale，transform-origin: bottom right，
  绝不引入水平位移。

    transform: translateY(14px) scale(.985);
    transition: opacity 160ms ease, transform 200ms cubic-bezier(.2,.8,.2,1);
    [data-open="true"] { transform: translateY(0) scale(1); opacity: 1; }

【列对齐 —— 这是最难的部分，必须实测不能用 ch 推算】
抽屉每一列要正对着气泡里对应的那个数字。用 ch 算术做不到：ch 是字符「0」的推进宽度，
而「tok/s」和细窄的「s」实际远比推算值窄，算出来的列永远差一截。

正确做法：运行时读取气泡每格的真实像素宽度，写成 CSS 变量供抽屉 grid 使用。

  // 气泡容器挂 ref，量五个 [data-metric] 格子
  useLayoutEffect(() => {
    if (!mounted) return undefined
    const measure = () => {
      const host = partsRef.current
      if (host === null) return
      const cells = host.querySelectorAll('[data-metric]')
      if (cells.length !== 5) return
      const widths = []
      for (const cell of cells) {
        const rect = cell.getBoundingClientRect()
        if (rect.width <= 0) return          // 未布局完成，保留 CSS 兜底
        widths.push(Math.round(rect.width * 100) / 100)
      }
      setColumnWidths((previous) =>
        previous !== null && previous.every((v, i) => v === widths[i]) ? previous : widths)
    }
    measure()
    window.addEventListener('resize', measure)
    let observer
    if (typeof ResizeObserver === 'function' && partsRef.current !== null) {
      observer = new ResizeObserver(() => measure())
      observer.observe(partsRef.current)
    }
    return () => { window.removeEventListener('resize', measure); observer?.disconnect() }
  }, [mounted])

  抽屉根节点把测得宽度发布成变量（按指标名绑定，不要靠位置）：
    '--dsh-rum-col-ttft':      `${columnWidths[0]}px`,
    '--dsh-rum-col-speed':     `${columnWidths[1]}px`,
    '--dsh-rum-col-tokens':    `${columnWidths[2]}px`,
    '--dsh-rum-col-total':     `${columnWidths[3]}px`,
    '--dsh-rum-col-amortized': `${columnWidths[4]}px`,

  行 grid（ch 表达式只作为测量落地前的兜底）：

八、首字时间在历史会话里为何曾经是空的（已修复，必须按此实现）
================================================================================

现象：首次启用时抽屉会从当前会话回填最近 10 条，但这些行首字列全是 —，
而 DSH 自带的「轨迹」页却对同样的步骤显示出首字延迟。

根因是数据流事实，不是计算缺失：
  timing.firstTokenTime 是【流式累积】状态。Chat 从 live token 增量里逐块累积它，
  而会话日志【不存 live chunk】。实测一个真实日志：787 个已结算消息，
  assistant/live-chunk 事件为 0 个。因此从日志回放的步骤没有这个字段。

但值是可恢复的：每条结算消息都带 data.stream —— 完整的 chunk 时间线，每个分片有自己的
时间戳。轨迹域正是从这里重建的：
  firstTokenTime = state.firstTokenTime ?? assistantStreamFirstTokenTime(event.data.stream)
（对打包的 run 用 time0 + dt 前缀和还原每个分片的绝对时间。）

Chat 的 finalNode() 【不透传】stream，所以插件从 legacy.nodes 拿不到它。
解法是读轨迹域：conversation.composer.dock 的 standardProps 里有 useTrajectory，
其快照的 eventNodes 中每个 assistant 节点都带已重建好的 timing.firstTokenTime。

    function firstTokenIndex(trajectorySnapshot) {

九、数据与持久化
================================================================================

localStorage 两个 key：

  1) 模式标记：dsh.recentUsageMetrics.mode.v1
     值为 "geek" 或 null（JSON）。非 "geek" 一律当作未启用。

  2) 历史：dsh.recentUsageMetrics.history.v1
     值为 JSON 数组，长度 ≤ 10，最新在最前。每项：

     {
       "key": "1:2",           // `${turn}:${step}`，用于去重
       "at": 1792663948028,    // 结束时刻
       "startMs": 1792663945000, // 步骤起点（补写首字时间时要用）
       "ttftMs": 2300,
       "totalMs": 4600,
       "tokens": 1024,
       "estimated": false,     // true 表示 tokens 是估算值
       "speed": 445,
       "amortized": 223
     }

  读取时对任何输入做归一化，任何异常都不得抛错：非数组 → 空；
  单项缺字段/非数字 → 丢弃该字段；超长 → 截断到 10。
  写入失败（配额满/被禁）不得抛错，只是本次不持久化。

  行为：
  - record(reading)：插到最前，按 key 去重，截断到 10，写盘。
  - seed(readings)：仅当历史为空时，取传入列表的最后 10 条倒序写入。
  - backfill(next)：整体替换为重新计算过的行（为首字时间补写用）。

十、中英文双语（i18n）—— 两个已修复的 bug，必须按此实现
================================================================================

【bug A：切回中文不生效（HMR 场景）】

locale 服务对同一个 (命名空间, 语言) 只允许一个占用者，重复注册直接抛错，
且只提供 register 返回的 disposer 作为释放手段。

因此 apply 被第二次执行时（HMR 重载，或旧 fiber 清理尚未执行就重新 apply）：
旧的 zh/en 还占着命名空间 → 新的 register 抛错 → 整个 locale effect 失败 →
新字典没进去，而旧字典可能已被旧 fiber 清掉 → zh 缺失 → 查找沿 fallback 落到 en。
结果就是「英文能显示，切不回中文」。

修复三要素，缺一不可：

    const DISPOSER_KEY = '__dshRecentUsageMetricsLocale'

    function releaseDictionaries() {
      const host = typeof globalThis !== 'undefined' ? globalThis : undefined
      if (host === undefined) return
      const previous = host[DISPOSER_KEY]
      if (typeof previous !== 'function') return
      delete host[DISPOSER_KEY]
      try { previous() } catch {}
    }

    ctx.effect(() => {
      releaseDictionaries()                        // ① 先释放上一代的占用
      const dispose = locale.register(NS, { zh, en })
      const host = globalThis
      host[DISPOSER_KEY] = dispose                 // ② disposer 必须挂 globalThis
      return () => {
        const owner = host[DISPOSER_KEY] === dispose   // ③ 只有仍是 owner 才释放
        if (owner) { delete host[DISPOSER_KEY]; dispose() }
      }
    }, 'dsh-recent-usage-metrics: zh/en strings')

  ① 注册前必须先 release，否则重复注册抛错。
  ② 不能存模块级变量：HMR 会重跑整个模块，模块变量重置为 undefined，
     而上一代占用仍存活，就永远释放不掉。
  ③ 不能无条件 dispose：重载时新一代先 apply 并写入 globalThis，
     随后退休 fiber 的清理才执行，无条件释放会删掉新一代刚注册的字典。

【bug B：重启 DSH 后变英文且切不回中文（冷启动场景）】

原先只声明 inject: ['slots']，然后在 apply 里用 ctx.get('locale') 探测服务是否存在。
冷启动时各插件启动顺序无保证，本插件可能先于 locale 插件启动，此时
ctx.get('locale') 返回 undefined，而 `if (locale !== undefined)` 把注册整段吞掉：
字典从未注册 → 槽位却声明了 locale: NS → 注入的 t 找不到字典 → 回落到 en 或原始 key。
失败完全静默，没有报错。

修复两处，必须同时满足：

  1) locale 声明为【硬依赖】：
       return { name: 'dsh-recent-usage-metrics', inject: ['slots', 'locale'], apply }
  2) apply 里直接读 ctx.locale，不再探测，也不要保留 undefined 判空：
       const locale = ctx.locale

  【禁止】退回 inject: ['slots'] + ctx.get('locale') 探测；
  【禁止】把 locale 相关 effect 包在「服务存在才执行」的分支里。

【bug C：configForms 也是同类问题】
设置行需要读原生 ui-chat 域的 performanceUsage 字段，该服务同样可能晚到。
不要用 ctx.get('configForms') 一次性探测（会把设置行永久锁在 fallback 值上），
改用 ctx.inject 等待：

    ctx.inject(['configForms'], (scope) => {
      let form = null
      try { form = scope.configForms.get('ui-chat') } catch { form = null }
      preference.bind(form)
      return () => preference.bind(null)
    })

  createPreference 要支持延迟绑定（bind），并能幂等地重新绑定。

十一、性能（实测数据，供判断是否需要优化）
================================================================================

【实测：Geek 未启用时几乎零开销】
所有定时器、事件监听、DOM 测量、渲染都在 `if (!geek) return null` 之后或被
if (!open) / if (!running) 提前返回。常驻的只有：
  - 四个 store 订阅（三个 useChat + 一个 useRows），每次 store 发布会话约 0.024 µs
  - 一个 <style> 元素、一次字典注册、一次 localStorage 读
按 25 次发布/秒计算约 0.0006 ms CPU/秒。可视为无影响。

【实测：流式期间的纯计算成本】
token 估算每 150 ms 重扫全部累积文本：
  英文 20k 字符 → 0.19 µs/次   → 0.001 ms/秒
  工具参数 3k   → 0.10 µs/次   → 0.001 ms/秒
  中文 2k 字符  → 28 µs/次     → 0.19 ms/秒
  中文 20k 字符 → 428 µs/次    → 2.9 ms/秒
中文路径比英文慢约 150 倍，因为 String.match(/[\u4e00-\u9fff]/g) 每命中一个字符都要
分配字符串对象，而英文零命中时返回 null、几乎不分配。即使极端情况也只占单核 0.3%。

重新渲染路径（filter + seen-set 重建）：
  200 条会话 → 约 4 µs/次
  2000 条会话 → 约 40 µs/次
按 25 chunk/秒 + 6.7 tick/秒，500 条会话约 0.33 ms CPU/秒。

结论：不需要为性能做特殊优化。若将来要优化，优先减少 nodes 全量扫描。

文件 9～11：测试
------------------------------------------------------------------
三个测试都用「把 client.js 跑在 vm 沙箱里 + 自建 hook 运行时 + DOM shim」的方式，
不需要浏览器，直接 node test/xxx.cjs 即可。

  test/lifecycle.cjs        主测试，覆盖：五指标计算、10 行上限与插入顺序、
                            固定宽度槽位、估算标记、平均值行、点击开合、
                            右缘对齐、轨迹域补写、工具参数实时计入、清理无残留
  test/repro-coldstart.cjs  断言 inject 含 locale、apply 读 ctx.locale、
                            首屏中文、双向切换、命名空间声明、偏好跟随
  test/repro-hmr.cjs        断言重载不撞名、只留一个声明、disposer 正确释放

  自建 hook 运行时的要点（否则测试会挂）：
  - 渲染要把 effect 的 cleanup 先跑一遍再重跑，且 frames 要跨渲染保留（用 visited Set），
    否则 hook 状态会丢、嵌套组件永远不更新。
  - useRef 直接实现为 frame.cells[i] = { kind:'ref', current:value }，不要二次求值。
  - 结束前用 setTimeout(() => process.exit(...), 50) 兜底，
    并断言 process.getActiveResourcesInfo() 里没有残留 timer。
